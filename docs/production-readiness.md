## 1. โดเมนและ DNS

- [ ] `meeting.example.com` เปิดได้และเป็น HTTPS
- [ ] Redirect ระหว่าง `www` กับ non-`www` ตั้งไว้แบบเดียว ไม่มี URL ซ้ำสองแบบ
- [ ] `dig +short CNAME meeting.example.com` ได้ค่าตรงกับที่ Vercel แสดง
- [ ] **MX record ของโดเมนหลักยังอยู่ครบ** — อีเมลองค์กรส่งและรับได้ปกติ
- [ ] ไม่มี DNS record เดิมที่จำเป็นสูญหาย (เทียบกับไฟล์สำรอง)
- [ ] TTL ปรับกลับเป็นค่าปกติ (เช่น 3600) หลังย้ายเสร็จ
- [ ] บันทึกวันหมดอายุโดเมนและเปิด auto-renewal แล้ว
- [ ] เปิด MFA ที่บัญชี registrar

```bash
curl -sI https://meeting.example.com | grep -iE "^(HTTP|strict-transport|content-security|x-frame|x-content-type)"
dig +short MX example.com
```

## 2. HTTPS และ Security headers

- [ ] SSL certificate สถานะ **Issued** และยังไม่ใกล้หมดอายุ
- [ ] มี `strict-transport-security` ใน response header
- [ ] มี `content-security-policy`
- [ ] มี `x-frame-options: DENY` และ `x-content-type-options: nosniff`
- [ ] ไม่มี header ที่เปิดเผยเวอร์ชันซอฟต์แวร์เกินจำเป็น

## 3. Environment variables

- [ ] `DATABASE_URL` เป็นเส้น **Transaction pooler พอร์ต 6543**
- [ ] **ไม่มี `DIRECT_URL` ใน Vercel**
- [ ] `DATABASE_SSL=true`
- [ ] `AUTH_SECRET` เป็นค่าสุ่มยาวและ **คนละค่ากับ staging**
- [ ] `APP_ENV=production` และ `NEXT_PUBLIC_APP_URL` เป็นโดเมนจริง
- [ ] `AUTH_ALLOW_SELF_REGISTER=false` (ถ้าต้องการให้เชิญเท่านั้น)
- [ ] `AUTH_ALLOWED_EMAIL_DOMAINS` ตั้งเป็นโดเมนอีเมลองค์กร
- [ ] `EMAIL_PROVIDER=resend` และคีย์เป็นใบของ production
- [ ] `LINE_PROVIDER=messaging-api` และใช้ค่าของ channel จริง
- [ ] `CRON_SECRET` ตั้งแล้ว
- [ ] กด **Redeploy** หลังใส่ตัวแปรครบแล้ว
- [ ] ตรวจว่าไม่มีความลับหลุดไปฝั่ง browser

```bash
npm run build
grep -ril "service_role\|LINE_CHANNEL\|EMAIL_API_KEY\|AUTH_SECRET" .next/static | head
# ต้องไม่พบไฟล์ใดเลย
```

## 4. ฐานข้อมูล

- [ ] `npm run db:migrate -- --status` ขึ้น "รันแล้ว" ทุกไฟล์
- [ ] **ไม่ได้ seed ข้อมูลตัวอย่างลง production**
- [ ] `/api/health` ตอบ `{"status":"ok","database":"ok"}`
- [ ] Row Level Security เปิดและ FORCE ครบทุกตารางข้อมูล
- [ ] Exclusion constraint กันจองซ้อนยังอยู่
- [ ] มีบัญชีผู้ดูแลระบบสูงสุดอย่างน้อย **2 คน**
- [ ] Backup เปิดใช้งาน และบันทึก RPO/RTO ไว้แล้ว
- [ ] **ทดสอบ restore จริงแล้ว** (ไม่ใช่แค่เปิดฟีเจอร์ไว้)

```sql
-- ตรวจ RLS
select relname, relrowsecurity, relforcerowsecurity from pg_class
where relname in ('bookings','profiles','audit_logs','rooms','user_roles','notification_jobs');
-- ทุกแถวต้องเป็น t, t

-- ตรวจตัวกันจองซ้อน
select conname from pg_constraint where conname = 'bookings_no_overlap';
-- ต้องได้ 1 แถว

-- ตรวจว่าไม่มีการจองซ้อนกันอยู่จริง (ต้องได้ 0 แถว)
select count(*) from bookings a join bookings b
  on a.room_id = b.room_id and a.id < b.id and a.blocked_period && b.blocked_period
where a.blocks_slot and b.blocks_slot;
```

## 5. อีเมล

- [ ] โดเมนส่งอีเมลสถานะ **Verified** ทุก record (SPF, DKIM, DMARC)
- [ ] `EMAIL_FROM` เป็นโดเมนที่ verify แล้ว
- [ ] `EMAIL_REPLY_TO` เป็นอีเมลที่มีคนดูแลจริง
- [ ] ทดสอบส่งไป **Gmail** แล้วไม่เข้า Junk
- [ ] ทดสอบส่งไป **Outlook / Microsoft 365** แล้วไม่เข้า Junk
- [ ] ทดสอบส่งไป **อีเมลองค์กร** แล้วไม่เข้า Junk
- [ ] ภาษาไทยในอีเมลแสดงถูกต้อง ไม่เป็นตัวต่างดาว
- [ ] ปุ่มในอีเมลกดได้และลิงก์ชี้ไปโดเมนจริง
- [ ] ไฟล์ปฏิทิน `.ics` เปิดแล้วเวลาตรงกับเวลาไทย
- [ ] อ่านบนมือถือได้ ไม่ต้องเลื่อนซ้ายขวา
- [ ] Webhook bounce/complaint ตั้งแล้วและทดสอบผ่าน

## 6. LINE

- [ ] Webhook สถานะ **Success** ในหน้า LINE Developers
- [ ] ปิด Auto-reply messages แล้ว
- [ ] ทดสอบเชื่อมบัญชีด้วยรหัส 8 ตัว สำเร็จ
- [ ] ทดสอบว่ารหัสที่หมดอายุหรือใช้แล้วใช้ซ้ำไม่ได้
- [ ] ทดสอบรับข้อความยืนยันการจอง / อนุมัติ / เตือนก่อนประชุม
- [ ] ทดสอบยกเลิกการเชื่อม แล้วไม่ได้รับข้อความอีก
- [ ] เปิด MFA ที่บัญชีเจ้าของ และมีผู้ดูแลสำรอง

## 7. สิทธิ์และความเป็นส่วนตัว

ทดสอบด้วยบัญชีจริงของแต่ละ Role

- [ ] **พนักงาน** จองได้ แต่ไม่เห็นเมนูหลังบ้าน และพิมพ์ URL `/admin` ตรงก็เข้าไม่ได้
- [ ] **พนักงาน** เรียก `POST /api/rooms` ได้ **403**
- [ ] **พนักงาน** แก้/ยกเลิกการจองของคนอื่นไม่ได้
- [ ] **ผู้ชม** ดูตารางได้แต่ไม่มีปุ่มจอง และเรียก API จองได้ 403
- [ ] **ผู้อนุมัติ** เห็นคิวรออนุมัติและอนุมัติได้
- [ ] **ผู้ดูแลห้อง** แก้ได้เฉพาะห้องในขอบเขตของตน
- [ ] การประชุมที่ตั้งเป็น **ส่วนตัว** ของคนอื่น ผู้ใช้ทั่วไปไม่เห็นเลย
- [ ] การประชุมที่ตั้งเป็น **แสดงเฉพาะว่าไม่ว่าง** เห็นแค่ช่วงเวลา ไม่เห็นหัวข้อและชื่อ
- [ ] ผู้ที่ยังไม่ล็อกอินถูกพาไปหน้าเข้าสู่ระบบ และ API ตอบ 401

## 8. งานตามเวลาและคิวงาน

- [ ] Vercel → Cron Jobs เห็นทั้งสองรายการ
- [ ] เรียก `/api/cron/dispatch` **โดยไม่ใส่ header** ได้ **403**
- [ ] เรียกด้วย `CRON_SECRET` ถูกต้อง ได้ 200
- [ ] จองหนึ่งรายการแล้วรอรอบ Cron → ได้รับอีเมลจริง
- [ ] หน้า **สถานะระบบ** ไม่มีงานค้างเกิน 15 นาที และไม่มีงานล้มเหลวถาวร
- [ ] เรียก Cron ซ้ำหลายรอบแล้วผู้ใช้ **ไม่ได้รับอีเมลซ้ำ** (idempotency)
- [ ] ทดสอบว่าห้องที่ตั้ง "ต้องเช็กอิน" ถูกปล่อยคืนเมื่อไม่มีการเช็กอิน

## 9. เทสต์อัตโนมัติ

- [ ] `npm run verify` ผ่าน (typecheck + lint + unit test)
- [ ] `npm run test:integration` ผ่านทั้งหมด
- [ ] `npm run test:e2e` ผ่านทั้งหมด (ทุกขนาดจอ)
- [ ] เทสต์ race condition (ยิงคำขอพร้อมกัน) สำเร็จเพียงรายการเดียว
- [ ] `npm run audit:prod` ได้ผล **found 0 vulnerabilities**
      (ตรวจเฉพาะ dependency ที่ใช้ตอนรันจริง ไม่รวมเครื่องมือของนักพัฒนา)

## 10. Accessibility และ Responsive

- [ ] ใช้งานได้ที่ความกว้าง **360px**, **768px**, **1024px** และจอกว้าง
- [ ] หน้าหลักไม่ต้องเลื่อนแนวนอน
- [ ] ซูม 200% แล้วยังใช้งานปุ่มจองได้
- [ ] ใช้คีย์บอร์ดเข้าถึงงานหลักได้ (Tab / Enter / Esc)
- [ ] ปิด dialog ด้วย Esc แล้ว focus กลับไปที่ปุ่มที่เปิด
- [ ] สถานะไม่ได้สื่อด้วยสีอย่างเดียว มีข้อความและสัญลักษณ์กำกับ
- [ ] ทุกฟิลด์ในฟอร์มมี label ที่ screen reader อ่านได้
- [ ] `npm run lighthouse -- http://<โดเมนจริง>/login` ได้ Performance และ
      Best Practices ไม่ต่ำกว่าค่าที่บันทึกไว้ใน [performance.md](performance.md)
- [ ] รับทราบว่า Accessibility จะได้ 96 ไม่ใช่ 100 เพราะสีส้มแบรนด์กับตัวอักษรขาว
      ยังไม่ผ่านเกณฑ์ contrast (เป็นการตัดสินใจเรื่องแบรนด์ที่ค้างอยู่ —
      ดู [performance.md](performance.md) ข้อ 7)

### ติดตั้งเป็นแอฟบนมือถือ (PWA)

- [ ] เปิดเว็บบนมือถือจริงแล้วกด "เพิ่มลงในหน้าจอหลัก" ได้ และไอคอนขึ้นถูกต้อง
- [ ] เปิดจากไอคอนแล้วไม่มีแถบที่อยู่เว็บ (โหมด standalone)
- [ ] ปิดเน็ตแล้วเปิดแอฟ เห็นหน้าอธิบายภาษาไทย ไม่ใช่หน้า error ของเบราว์เซอร์
- [ ] ล็อกเอาต์แล้วเปิดใหม่ **ต้องไม่เห็นข้อมูลของคนก่อนจากแคช**
      (ข้อนี้สำคัญที่สุด — บังคับด้วยเทสต์ `tests/e2e/pwa.spec.ts` อยู่แล้ว
      แต่ควรลองด้วยมือบนเครื่องจริงอีกครั้ง)

## 13. แผน Cutover วันเปิดใช้งาน

| หัวข้อ | รายละเอียด |
|---|---|
| วันเวลาที่เปิดใช้ | (กรอก — เลือกช่วงที่คนใช้งานน้อย เช่น เย็นวันศุกร์) |
| ผู้ดูแลระหว่าง cutover | (กรอกชื่อ + เบอร์) |
| แจ้งผู้ใช้ล่วงหน้า | (กรอกวันที่และช่องทาง) |
| ช่วงเฝ้าระวังหลังเปิด | 2 ชั่วโมงแรก และตรวจอีกครั้งเช้าวันทำการถัดไป |

### เกณฑ์ Go / No-go

**เปิดใช้งานได้เมื่อ** ข้อ 1–12 ติ๊กครบ และ smoke test ผ่านทั้งหมด

**เลื่อนออกไปถ้ามีข้อใดข้อหนึ่ง**

- `/api/health` ไม่ตอบ `ok`
- อีเมลยืนยันการจองไม่ถึงปลายทาง
- ทดสอบสิทธิ์แล้วพบว่าผู้ใช้เห็นข้อมูลที่ไม่ควรเห็น
- ยังไม่เคยทดสอบ restore ฐานข้อมูล
- ไม่มีผู้ดูแลระบบสูงสุดคนที่สอง

### Smoke test หลังเปิดใช้งาน (ทำทันที)

- [ ] เข้าสู่ระบบด้วยบัญชีจริง
- [ ] เปิดปฏิทิน สลับ วัน / สัปดาห์ / เดือน
- [ ] ค้นหาห้องและค้นหาช่วงเวลาว่าง
- [ ] จองห้องหนึ่งรายการ → เห็นในปฏิทินทันที
- [ ] ได้รับอีเมลยืนยัน
- [ ] จองห้องที่ต้องอนุมัติ → ผู้อนุมัติได้รับแจ้งเตือนและอนุมัติได้
- [ ] แก้ไขและยกเลิกรายการทดสอบ → ผู้เข้าร่วมได้รับแจ้ง
- [ ] เปิดจากมือถือจริงหนึ่งเครื่อง
- [ ] ตรวจหน้า **สถานะระบบ** ว่าไม่มีงานค้าง
- [ ] ตรวจ **บันทึกการใช้งาน** ว่าบันทึกรายการทดสอบไว้ครบ

### แผนย้อนกลับ

ถ้าพบปัญหาร้ายแรงภายใน 2 ชั่วโมงแรก

1. Rollback deployment ที่ Vercel (**⋯ → Promote to Production** ของ deployment ก่อนหน้า)
2. ถ้าต้องหยุดการแจ้งเตือน ให้ปิด Cron `/api/cron/dispatch`
3. แจ้งผู้ใช้ให้จดการจองไว้ก่อนผ่านช่องทางที่ไม่พึ่งระบบนี้
4. บันทึกเหตุการณ์ สาเหตุ และสิ่งที่ต้องแก้ก่อนลองใหม่

รายละเอียดอยู่ใน [runbooks.md](runbooks.md#rollback-runbook)

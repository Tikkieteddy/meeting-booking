# การตัดสินใจเชิงสถาปัตยกรรม (Architecture Decision Records)

บันทึกว่า "ตัดสินใจอะไร เพราะอะไร แลกอะไรไป" เพื่อให้คนที่มาทำต่อเข้าใจเหตุผล
และรู้ว่าจุดไหนเปลี่ยนได้ จุดไหนเปลี่ยนแล้วกระทบมาก

---

## ADR-001 — กันการจองซ้อนด้วย exclusion constraint ที่ฐานข้อมูล

**บริบท** บรีฟข้อ 6 และ AC04 กำหนดว่า "ห้ามพึ่งการตรวจเฉพาะหน้าเว็บ" และเมื่อหลายคำขอ
เข้ามาพร้อมกันต้องสำเร็จได้เพียงรายการเดียว

**ทางเลือกที่พิจารณา**

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| ตรวจในโค้ดก่อน INSERT | เขียนง่าย ข้อความ error คุมได้ | มีช่องว่างระหว่างตรวจกับบันทึก สองคำขอพร้อมกันผ่านได้ทั้งคู่ |
| ล็อกตารางทั้งใบ | กันได้จริง | ทุกคนจองห้องไหนก็ต้องรอกันหมด ระบบช้าลงมาก |
| **Exclusion constraint + advisory lock ต่อห้อง** | ฐานข้อมูลรับประกันเอง ล็อกแค่ห้องเดียว | ข้อความ error ของฐานข้อมูลอ่านไม่รู้เรื่อง ต้องแปลเอง |

**การตัดสินใจ** ใช้ exclusion constraint เป็นหลักประกันสุดท้าย

```sql
EXCLUDE USING gist (room_id WITH =, blocked_period WITH &&) WHERE (blocks_slot)
```

และใช้ `pg_advisory_xact_lock(room_id)` ก่อนตรวจ เพื่อให้กรณีปกติได้ข้อความอธิบาย
ว่าชนกับการจองใด (ไม่ใช่ error ดิบของฐานข้อมูล)

**ผลที่แลกไป** ต้องจับ error code `23P01` ของ PostgreSQL แล้วแปลเป็นข้อความไทย
และต้องใช้ extension `btree_gist`

**หลักฐานว่าใช้ได้** เทสต์ integration ยิง 10 คำขอพร้อมกันในช่วงเวลาเดียวกัน
ได้ผลสำเร็จ 1 รายการและ conflict 9 รายการทุกครั้ง

## ADR-002 — เก็บเวลา buffer เป็น snapshot บนแถวการจอง

**บริบท** ห้องมีเวลา buffer ก่อน/หลังประชุม (บรีฟข้อ 6) ซึ่งผู้ดูแลระบบแก้ได้ภายหลัง

**การตัดสินใจ** คัดลอกค่า buffer ของห้อง ณ เวลาที่จอง ลงคอลัมน์
`buffer_before_minutes` / `buffer_after_minutes` บนแถวการจอง
แล้วให้ trigger คำนวณ `blocked_period` จากค่านั้น

**เหตุผล** ถ้าอ่าน buffer จากตารางห้องแบบสด ๆ การเปลี่ยนนโยบายห้องจะทำให้
`blocked_period` ของการจองเก่าทุกแถวขยับ ซึ่งอาจทำให้การจองที่เคยถูกต้อง
กลายเป็นชนกันย้อนหลัง และ exclusion constraint จะปฏิเสธการแก้ไขใด ๆ ต่อไป

**ผลที่แลกไป** การจองเก่าใช้ buffer เดิม ถ้าต้องการให้ใช้ค่าใหม่ทั้งหมด
ต้องเขียน migration อัปเดตเฉพาะการจองในอนาคต

## ADR-003 — ใช้ระบบยืนยันตัวตนของตัวเอง ไม่ใช้ Supabase Auth

> ⚠️ **ข้อนี้ต่างจากที่บรีฟระบุ** จึงอธิบายเหตุผลไว้ละเอียด

**บริบท** บรีฟข้อ 13 แนะนำ Supabase สำหรับ Database, Authentication, Storage และ RLS
เอกสารส่งต่อสรุปว่า "ใช้ Supabase Auth ตามบรีฟ" เพราะได้ยืนยันอีเมล ลืมรหัสผ่าน
กันเดารหัสผ่าน และ Row Level Security มาให้ในตัว

**สิ่งที่พบตอนลงมือ**

1. Supabase Auth ต้องมีโปรเจกต์จริงและคีย์จริงจึงจะทำงานได้
   ในเซสชันนี้ไม่มีคีย์ (และไม่ควรมี) → ถ้าผูกกับ Supabase Auth
   จะไม่มีอะไรทดสอบได้เลยจนกว่าผู้ใช้จะตั้งค่าเสร็จ
   ซึ่งขัดกับบรีฟข้อ 17 ที่ห้ามถือว่างานเสร็จถ้ายังมีฟังก์ชันที่ทดสอบไม่ได้
2. **Row Level Security ไม่ได้ผูกกับ Supabase Auth** RLS เป็นความสามารถของ PostgreSQL
   ใช้ได้โดยไม่ต้องใช้ Supabase Auth
3. โปรเจกต์เดิมของผู้ใช้ (`register`) ที่ขึ้น production แล้ว ก็เขียนระบบล็อกอินเอง
   ทีมจึงคุ้นเคยกับแนวทางนี้อยู่แล้ว

**การตัดสินใจ** เขียนระบบยืนยันตัวตนเอง โดยทำสิ่งที่บรีฟต้องการให้ครบทุกข้อ

| สิ่งที่บรีฟต้องการ | ทำอย่างไรในระบบนี้ |
|---|---|
| ยืนยันอีเมล | โทเค็นใช้ครั้งเดียวอายุ 24 ชม. ส่งผ่านคิวอีเมล |
| ลืมรหัสผ่าน | โทเค็นอายุ 60 นาที ใช้แล้วเตะทุกอุปกรณ์ออก |
| กันเดารหัสผ่าน | จำกัด 8 ครั้ง/15 นาที ต่ออีเมล และ 24 ครั้ง/15 นาที ต่อ IP |
| เชิญผู้ใช้โดย Admin | โทเค็นคำเชิญอายุ 7 วัน |
| Session timeout / ออกทุกอุปกรณ์ | ตาราง `user_sessions` เพิกถอนได้ทีละใบหรือทั้งหมด |
| Row Level Security | เปิด RLS + `FORCE ROW LEVEL SECURITY` ทุกตารางข้อมูล |
| เก็บรหัสผ่านอย่างปลอดภัย | scrypt (`node:crypto`) ไม่มี native dependency ที่ build บน Vercel ยาก |

**ผลที่แลกไป**

- ต้องดูแลโค้ดยืนยันตัวตนเอง (ประมาณ 400 บรรทัด มีเทสต์ครอบ)
- ยังไม่มี SSO (Google Workspace / Microsoft Entra ID) — เตรียมจุดเชื่อมไว้แล้ว
- ไม่ได้ใช้หน้า Auth UI ที่ Supabase ให้มา

**ทางกลับ ถ้าต้องการย้ายไป Supabase Auth ภายหลัง**

จุดเชื่อมทั้งหมดอยู่ใน `src/lib/auth/` เพียงสามไฟล์

1. `session.ts` — เปลี่ยน `resolveSession()` ให้อ่าน JWT ของ Supabase แทน cookie ของเรา
2. `service.ts` — เปลี่ยนให้เรียก Supabase Auth API แทนการจัดการรหัสผ่านเอง
3. `profiles.id` ต้องใช้ค่าเดียวกับ `auth.users.id` ของ Supabase (เขียน migration แมปให้)

**ฟังก์ชัน `app.current_user_id()` ในฐานข้อมูลรองรับไว้แล้วทั้งสองทาง** —
อ่านจาก session variable ของเราก่อน ถ้าไม่มีจะอ่านจาก `request.jwt.claims` ของ PostgREST
ดังนั้น **RLS policy ทั้งหมดไม่ต้องแก้เลย** เมื่อย้ายไป Supabase Auth

## ADR-004 — ใช้ SQL ล้วน ไม่ใช้ ORM

**การตัดสินใจ** ใช้ `pg` โดยตรง เขียน SQL เอง และเขียน migration เป็นไฟล์ `.sql`

**เหตุผล**

- ฟีเจอร์หัวใจของระบบ (exclusion constraint, `tstzrange`, GiST index, RLS policy,
  `FOR UPDATE SKIP LOCKED`) เป็นของเฉพาะ PostgreSQL ซึ่ง ORM ส่วนใหญ่รองรับไม่ครบ
  ต้องเขียน raw SQL อยู่ดี
- ควบคุมขอบเขต transaction ได้แน่นอน ซึ่งจำเป็นเพราะต้องตั้ง session variable
  ให้ RLS ในทรานแซกชันเดียวกับงานหลัก
- ลด dependency ทำให้ build เร็วและพื้นที่ความเสี่ยงเล็ก

**ผลที่แลกไป** ไม่มี type ที่ generate จาก schema ให้อัตโนมัติ — ต้องประกาศชนิดผลลัพธ์
ของ query เอง ทีมต้องอ่าน SQL ได้

## ADR-005 — RLS: `FORCE ROW LEVEL SECURITY` และการยกระดับสิทธิ์แบบมีขอบเขต

**บริบท** แอปต่อฐานข้อมูลด้วยบัญชี *เจ้าของตาราง* ซึ่งโดยปริยาย **ข้าม RLS ทั้งหมด**
ถ้าไม่เปิด `FORCE` RLS จะไม่มีผลเลยกับคำสั่งที่มาจากแอป

**ปัญหาที่พบระหว่างพัฒนา** ตอนแรกเปิด `FORCE` เฉพาะตารางข้อมูล แต่เว้นตาราง RBAC
(`user_roles` ฯลฯ) ไว้ เพราะกลัว policy เรียกวนซ้ำ (policy ของ `user_roles`
เรียก `app.has_permission()` ซึ่งอ่าน `user_roles` เอง)

**เทสต์ integration จับได้ว่านี่เป็นช่องโหว่จริง** — ผู้ใช้ที่ล็อกอินแล้วสามารถ
`INSERT INTO user_roles` เพื่อยกสิทธิ์ตัวเองเป็น `super_admin` ได้ที่ชั้นฐานข้อมูล
(API ยังกันไว้ แต่ถ้ามีโค้ดเส้นใดลืมตรวจก็จะหลุด)

**การตัดสินใจ** (migration 007)

1. เปิด `FORCE ROW LEVEL SECURITY` **ทุกตาราง** รวมตาราง RBAC
2. เขียน policy ของ `user_roles` โดย **ไม่เรียกฟังก์ชันที่อ่าน `user_roles`** จึงไม่วนซ้ำ
   - อ่าน: เห็นเฉพาะสิทธิ์ของตัวเอง
   - เขียน: เฉพาะ service context
3. เพิ่มตัวช่วย `asService(sql, fn)` ที่ยกระดับสิทธิ์ **เฉพาะคำสั่งในบล็อกนั้น**
   ภายใน transaction เดียวกัน แล้วคืนสิทธิ์เดิมทุกกรณี

**ใช้ `asService` ที่ไหนบ้าง และทำไมปลอดภัย**

| จุดที่ใช้ | เหตุผล | อะไรกันไว้ |
|---|---|---|
| เขียน `audit_logs` | audit เป็นตารางของระบบ ผู้ใช้เขียนตรงไม่ได้ | เขียนได้เท่านั้น แก้/ลบไม่ได้เลย |
| ใส่งานลงคิวแจ้งเตือน | ต้องแจ้งผู้เข้าร่วมและผู้อนุมัติ ซึ่งเป็นคนอื่น | ผู้ใช้อ่านคิวไม่ได้ และเนื้อหามาจาก template ของระบบ |
| สร้างแถวคำขออนุมัติ | ผู้จองไม่มีสิทธิ์เขียนตาราง `approvals` | สร้างตามรายชื่อผู้อนุมัติของห้องเท่านั้น |
| จับคู่ผู้เข้าร่วมกับบัญชี | RLS เปิดให้อ่านโปรไฟล์เฉพาะของตัวเอง | ค้นด้วยอีเมลที่ผู้จองพิมพ์เข้ามาทีละรายการ ไม่ได้เปิดให้ไล่ดูรายชื่อทั้งองค์กร |
| เสนอคิวรอ / อ่านค่าตั้งของผู้จอง | ข้อมูลของผู้ใช้คนอื่น | เกิดจากการยกเลิก/อนุมัติที่ผ่านการตรวจสิทธิ์แล้ว |
| ให้/ถอน Role, อ่าน role ของผู้อื่น | `user_roles` เขียนได้เฉพาะ service | ผ่าน `requirePermission('role:manage')` และบันทึก audit ทุกครั้ง |

**ผลที่แลกไป** ต้องระวังไม่เรียก `asService` ครอบคำสั่งที่รับข้อมูลดิบจากผู้ใช้
ไปเขียนตารางธุรกิจ — มีคอมเมนต์กำกับไว้ทุกจุดและอธิบายกฎไว้ในฟังก์ชัน

## ADR-006 — ปิดบังข้อมูลส่วนตัวด้วย view ที่ฐานข้อมูล ไม่ใช่แค่ที่ UI

**บริบท** บรีฟข้อ 16 กำหนดว่าการประชุม Private ต้องเปิดเผยเฉพาะผู้มีสิทธิ์
ผู้ไม่มีสิทธิ์เห็นเพียงว่าไม่ว่างและช่วงเวลา

**การตัดสินใจ** สองชั้น

1. **RLS ตัดแถว** — การจองแบบ `private` ของผู้อื่นไม่ปรากฏในผลลัพธ์เลย
2. **View ปิดบังฟิลด์** — `app.v_calendar_bookings` แทนหัวข้อด้วย `'ไม่ว่าง'`
   และคืน `booker_name` เป็น `NULL` สำหรับการจองแบบ `busy_only`
   โดยตั้ง `security_invoker = on` ให้ RLS ของตารางต้นทางยังมีผลกับผู้เรียก

**ผลที่แลกไป** ต้อง query ผ่าน view สำหรับงานแสดงผล และ query ตารางตรงสำหรับงานที่
ต้องการข้อมูลเต็ม (เช่น เจ้าของแก้การจองตัวเอง) ต้องระวังไม่สลับกัน

**ทางเลือกที่ไม่เลือก** ปิดบังที่ชั้น API เท่านั้น — ถูกปฏิเสธเพราะถ้ามี endpoint ใหม่
ที่ลืมปิดบัง ข้อมูลจะรั่วทันที

## ADR-007 — คิวงานแจ้งเตือนในตารางฐานข้อมูล ไม่ใช้ message broker

**บริบท** ต้องส่งอีเมล/LINE พร้อม retry, backoff, idempotency และบันทึกผลการส่ง
(บรีฟข้อ 10) บนสถาปัตยกรรม serverless

**ทางเลือกที่พิจารณา**

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| ส่งทันทีใน request | ง่ายสุด | ผู้ใช้รอนาน และถ้าผู้ให้บริการล่มการจองจะล้มไปด้วย |
| Redis / SQS / broker | ออกแบบมาเพื่องานนี้ | เพิ่มบริการที่ต้องดูแล ต้องมีคีย์เพิ่ม ขัดกับความต้องการ "แยกเอกเทศแต่เรียบง่าย" |
| **ตารางคิวใน PostgreSQL + Cron** | ไม่เพิ่มบริการ ตรวจย้อนหลังได้ด้วย SQL อยู่ในทรานแซกชันเดียวกับการจอง | ความหน่วงเท่ากับรอบ Cron (สูงสุด 5 นาที) |

**การตัดสินใจ** ใช้ตาราง `notification_jobs` + `FOR UPDATE SKIP LOCKED`
ทำให้ worker หลายตัวทำงานพร้อมกันได้โดยไม่ส่งซ้ำ และ `dedupe_key` เป็น unique
จึงกันการใส่งานซ้ำตั้งแต่ต้นทาง

**ผลที่แลกไป** การแจ้งเตือนไม่ได้ทันทีทันใด (รอรอบ Cron)
ซึ่งยอมรับได้สำหรับอีเมลยืนยันการจอง แต่ถ้าต้องการเร็วกว่านี้
สามารถเรียก worker ตรงหลังบันทึกสำเร็จได้โดยไม่ต้องแก้โครงสร้าง

## ADR-008 — Rate limit เก็บใน PostgreSQL

**บริบท** Vercel เป็น serverless — ตัวแปรในหน่วยความจำไม่ถูกแชร์ข้าม instance
การนับใน memory จึงกันอะไรไม่ได้จริง

**การตัดสินใจ** ใช้ตาราง `rate_limit_counters` แบบ fixed window
ด้วย `INSERT ... ON CONFLICT DO UPDATE ... RETURNING hits` ซึ่งเป็น atomic ในคำสั่งเดียว

**ผลที่แลกไป** เพิ่ม query หนึ่งครั้งต่อการเรียกที่ถูกจำกัด
และ fixed window ยอมให้เกิด burst ที่ขอบหน้าต่างได้ (ยอมรับได้สำหรับกรณีใช้งานนี้)
ถ้าต้องการแม่นกว่านี้ให้เปลี่ยนไปใช้ sliding window หรือ Upstash Redis
โดยแก้เฉพาะ `src/lib/util/rate-limit.ts`

## ADR-009 — ไม่แสดงสามมุมมองปฏิทินพร้อมกัน

**บริบท** ภาพประกอบในบรีฟแสดง Day / Week / Month เรียงกันสามช่อง
แต่บรีฟข้อ AC01 ระบุชัดว่าหน้าจอจริงห้ามแสดงทั้งสามมุมมองพร้อมกัน

**การตัดสินใจ** ยึดตาม AC01 — ภาพนั้นคือภาพโปสเตอร์โชว์ดีไซน์ ไม่ใช่หน้าจอใช้งานจริง
สิ่งที่ยกมาจากภาพคือ *แนวทางด้านภาพ* (สีส้ม TNN, การ์ดมุมโค้ง, เงานุ่ม, โทนมินิมอล,
เส้นเวลาปัจจุบันสีแดง, จุดสี 4 ระดับใน Month View) ไม่ใช่ *การจัดวาง*

หน้าจอจริงมีพื้นที่ปฏิทินเดียว เปลี่ยนเนื้อหาตามมุมมองที่เลือก
โดยห้อง วันที่ และตัวกรองคงค่าเดิม (เก็บไว้ใน URL ด้วย จึงแชร์ลิงก์และกดย้อนกลับได้)
มีเทสต์ e2e ยืนยันว่าบนหน้าจอมี `section[aria-label^="ปฏิทิน"]` เพียงหนึ่งชุดเสมอ

## ADR-010 — ไม่ใช้ไลบรารี UI component และไม่โหลดฟอนต์จากภายนอก

**การตัดสินใจ** เขียน component เอง (ปุ่ม ฟิลด์ modal/drawer toast) และใช้ฟอนต์ระบบ

**เหตุผล**

- ควบคุม accessibility ได้เต็มที่: focus trap, คืน focus, `aria-*`, ปิดด้วย Esc,
  ขนาดเป้าแตะ 44px, เคารพ `prefers-reduced-motion`
- CSP ตั้งได้เข้มขึ้นเพราะไม่ต้องอนุญาตโดเมนภายนอกสำหรับฟอนต์
- ไม่ต้องดาวน์โหลดฟอนต์ตอน build จึง build ได้แม้เครือข่ายถูกจำกัด
- ขนาด JavaScript ที่ส่งไปเบราว์เซอร์เล็ก (~103 KB shared)

**ผลที่แลกไป** ต้องดูแล component เอง และหน้าตาฟอนต์ต่างกันเล็กน้อยระหว่าง
Windows / macOS / Android (ทุกระบบมีฟอนต์ไทยที่อ่านได้อยู่แล้ว)

## ADR-011 — ใช้ชื่อ repository ที่ผู้ใช้สร้างไว้จริง

**บริบท** เอกสารส่งต่อวางแผนใช้ชื่อ `Tikkieteddy/tnn-meeting`
แต่เซสชันนี้ผูกกับ repository ชื่อ `tikkieteddy/meeting-booking`

**การตัดสินใจ** ทำงานใน repository ที่ผูกไว้จริง และไม่สร้าง repository ใหม่
โค้ดไม่มีที่ไหนอ้างอิงชื่อ repository ดังนั้นการเปลี่ยนชื่อภายหลังไม่กระทบระบบ
(ชื่อโปรเจกต์ใน `package.json` ยังเป็น `tnn-meeting` ตามชื่อระบบ)

## สิ่งที่ยังไม่ได้ทำ และเหตุผล

| เรื่อง | สถานะ | เหตุผล / สิ่งที่ต้องทำต่อ |
|---|---|---|
| SSO (Google Workspace / Entra ID) | ยังไม่ทำ | บรีฟข้อ 7.1 ระบุว่า "เตรียมจุดเชื่อมไว้ภายหลัง" — จุดเชื่ออยู่ใน `src/lib/auth/` |
| อัปโหลดไฟล์แนบในการจอง | ยังไม่ทำ | บรีฟข้อ 5.1 ระบุว่าเป็น optional ต้องตั้ง Supabase Storage bucket + RLS ก่อน |
| อัปโหลดรูปห้องประชุม | รับเป็น URL ได้แล้ว | ยังไม่มีหน้าอัปโหลด — ใส่ URL รูปที่โฮสต์ไว้แล้วได้ทันที |
| เชื่อมปฏิทินภายนอก (Google/Outlook) แบบสองทาง | ยังไม่ทำ | บรีฟระบุว่า "เตรียมไว้ภายหลัง" — ปัจจุบันให้ไฟล์ `.ics` ซึ่งเพิ่มลงปฏิทินได้ |
| Realtime subscription | ใช้การโหลดซ้ำแทน | ปฏิทินโหลดใหม่เมื่อเปลี่ยนมุมมอง/วัน/ห้อง และหลังทำรายการ เพียงพอกับการใช้งานจริง ถ้าต้องการ realtime ให้เปิด Supabase Realtime บนตาราง `bookings` |
| Custom role ที่สร้างเองจากหน้าเว็บ | โครงสร้างพร้อมแล้ว | ตาราง `roles`/`role_permissions` รองรับแล้ว ยังไม่มีหน้า UI สำหรับสร้าง role ใหม่ |
| ภาษาอังกฤษครบทุกข้อความ | แปลบางส่วน | โครงสร้าง i18n พร้อม ข้อความไทยครบ อังกฤษแปลคำที่ใช้บ่อย คีย์ที่ยังไม่แปลจะ fallback เป็นไทย |

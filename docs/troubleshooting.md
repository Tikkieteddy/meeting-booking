ถ้าแก้ตามนี้ไม่ได้ ให้ดู [runbooks.md](runbooks.md) ซึ่งเป็นขั้นตอนรับมือเหตุการณ์แบบเต็ม

ค่า `correlationId` จาก response header `x-correlation-id` (ถ้ามี)

## หมวด: ติดตั้งบนเครื่องตัวเอง

### `ตั้งค่า Environment variable ไม่ครบหรือไม่ถูกต้อง`

ข้อความ error จะบอกชื่อตัวแปรที่ขาดให้ตรง ๆ

```
ตั้งค่า Environment variable ไม่ครบหรือไม่ถูกต้อง:
  DATABASE_URL: ต้องตั้งค่า DATABASE_URL
  AUTH_SECRET: AUTH_SECRET ต้องยาวอย่างน้อย 32 ตัวอักษร
```

**แก้:** `cp .env.example .env.local` แล้วเติมค่า อย่างน้อย `DATABASE_URL` และ `AUTH_SECRET`

```bash
openssl rand -base64 48   # ใช้เป็น AUTH_SECRET
```

### `connect ECONNREFUSED 127.0.0.1:5432`

PostgreSQL ยังไม่ทำงาน หรือ connection string ผิด

```bash
pg_isready                      # ตรวจว่าฐานข้อมูลตอบสนอง
# macOS:  brew services start postgresql
# Linux:  sudo service postgresql start
```

### `database "tnn_meeting" does not exist`

```bash
createdb tnn_meeting
createdb tnn_meeting_test
npm run db:migrate
npm run db:seed
```

### `password authentication failed for user ...`

รหัสผ่านในconnection string ผิด — copy ใหม่จาก Supabase Dashboard
(Settings → Database) และอย่าลืมแทนคำว่า `[YOUR-PASSWORD]` ด้วยรหัสจริง

### `self signed certificate` หรือ `SSL required`

ตั้ง `DATABASE_SSL=true` ใน `.env.local` (จำเป็นเมื่อต่อ Supabase)

### `permission denied for schema public`

ใช้ connection string ของบทบาทที่สิทธิ์ไม่พอ — ใช้เส้นของผู้ใช้ `postgres`
ตามที่ Supabase Dashboard ให้มา

### เทสต์ integration ขึ้นว่า "ชื่อฐานข้อมูลของเทสต์ต้องมีคำว่า test"

เป็นการป้องกันไม่ให้เผลอล้างฐานข้อมูลจริง สร้างไฟล์ `.env.test.local`

```bash
TEST_DATABASE_URL=postgresql://user:pass@127.0.0.1:5432/tnn_meeting_test
```

### `npm run build` ล้มเหลวด้วย `This module cannot be imported from a Client Component`

มีไฟล์ที่ `'use client'` เผลอ import โมดูลฝั่ง server (ไฟล์ที่มี `import 'server-only'`)

**แก้:** ถ้าเป็นแค่ *ชนิดข้อมูล* ให้ใช้ `import type { X } from ...`
ถ้าเป็น *ฟังก์ชัน* ให้ย้ายฟังก์ชันนั้นไปไฟล์ที่ไม่มี `server-only`
(รูปแบบเดียวกับ `calendar.ts` ที่แยกส่วนบริสุทธิ์ออกเป็น `calendar-shared.ts`)

## หมวด: DNS และโดเมน

### สถานะใน Vercel ค้างที่ `Invalid Configuration` (DNS pending)

1. ตรวจว่าใส่ค่าตรงกับที่ Vercel แสดง (ห้ามเดา)

```bash
dig +short CNAME meeting.example.com
```

2. **ชื่อ host ผิดเป็นสาเหตุที่พบบ่อยที่สุด** — ผู้ให้บริการ DNS หลายรายเติมโดเมน
   ต่อท้ายให้เอง ถ้าใส่ `meeting.example.com` แล้วกลายเป็น
   `meeting.example.com.example.com` ต้องใส่แค่ `meeting`
3. ถ้าใช้ Cloudflare ต้องตั้งเป็น **DNS only** ไม่ใช่ Proxied
4. DNS ใช้เวลากระจาย 5 นาทีถึง 48 ชั่วโมง ตาม TTL เดิม — รอแล้วกด Refresh

### SSL ค้างที่ `pending` นานเกิน 1 ชั่วโมง

- ตรวจว่า DNS ผ่านก่อน (ข้อบน) เพราะ SSL ออกหลัง DNS ถูกต้อง
- ตรวจว่ามี **CAA record** ขวางอยู่หรือไม่

```bash
dig +short CAA example.com
```

ถ้ามี CAA ที่ไม่ได้อนุญาตผู้ออก certificate ที่ Vercel ใช้ ให้เพิ่มเข้าไป
หรือ **ลบ CAA ออกถ้าองค์กรไม่มีนโยบายเฉพาะ**

### อีเมลองค์กรล่มหลังแก้ DNS

**เรื่องเร่งด่วนที่สุด — แก้ก่อนเรื่องอื่นทั้งหมด**

```bash
dig +short MX example.com
```

ถ้าไม่ได้ค่าหรือได้ค่าผิด ให้นำ MX record เดิมกลับไปใส่ทันทีจากไฟล์สำรอง
(ดู [dns-sheet.md](dns-sheet.md) ขั้นที่ 1)

## หมวด: เข้าสู่ระบบ

### ผู้ใช้บอกว่าเข้าสู่ระบบไม่ได้ แต่รหัสผ่านถูก

| สาเหตุ | ตรวจอย่างไร | แก้อย่างไร |
|---|---|---|
| ใส่ผิดหลายครั้งจนถูกจำกัด | ขึ้นข้อความ "พยายามเข้าสู่ระบบบ่อยเกินไป" | รอ 15 นาที หรือใช้ "ลืมรหัสผ่าน" |
| บัญชีถูกระงับ/ปิด | หน้า ผู้ใช้และสิทธิ์ ดูสถานะ | เปลี่ยนสถานะเป็น "ใช้งานได้" |
| ยังไม่ตั้งรหัสผ่านจากคำเชิญ | สถานะเป็น "รอตั้งรหัสผ่าน" | ส่งคำเชิญใหม่ |
| อีเมลนอกโดเมนที่อนุญาต | ดูค่า `AUTH_ALLOWED_EMAIL_DOMAINS` | เพิ่มโดเมน หรือใช้อีเมลองค์กร |

### ล็อกอินสำเร็จแล้วเด้งกลับหน้าเข้าสู่ระบบทันที

cookie ไม่ถูกเก็บ

| สาเหตุ | แก้อย่างไร |
|---|---|
| `NEXT_PUBLIC_APP_URL` ไม่ตรงกับโดเมนที่ใช้เปิดเว็บ | ตั้งให้ตรง แล้ว Redeploy (ธง Secure ของ cookie อิงค่านี้) |
| เปิดผ่าน `www` แต่ตั้งค่าเป็น non-`www` | ตั้ง redirect ให้เหลือ host เดียว |
| เบราว์เซอร์ปิดการรับ cookie | ตรวจการตั้งค่าเบราว์เซอร์ |

### ผู้ใช้ทุกคนหลุดออกจากระบบพร้อมกัน

`AUTH_SECRET` ถูกเปลี่ยน (อาจตั้งใจตอนหมุนเวียนคีย์) เซสชันเดิมใช้ต่อไม่ได้
**เป็นพฤติกรรมที่ถูกต้อง** — แจ้งผู้ใช้ให้ล็อกอินใหม่

## หมวด: การจอง

### "ช่วงเวลานี้ถูกจองไปแล้ว" แต่ปฏิทินดูว่าง

| สาเหตุ | อธิบาย |
|---|---|
| มีเวลาเตรียมห้อง (buffer) | ห้องกันเวลาก่อน/หลังประชุมไว้ — ดูค่าที่หน้าจัดการห้อง |
| มีคนจองตัดหน้าพอดี | ปฏิทินยังไม่รีเฟรช — โหลดหน้าใหม่ |
| การจองนั้นเป็นแบบส่วนตัว | ผู้ใช้ทั่วไปไม่เห็นแถวนั้นแต่ห้องถูกกันไว้จริง |
| อยู่ในช่วงปิดปรับปรุง | จะเห็นแถบลายทแยงในปฏิทิน |

### จองไม่ได้ทั้งที่เวลาว่าง

อ่านข้อความบนหน้าจอก่อน — ระบบบอกสาเหตุตรง ๆ ทุกกรณี
ตารางความหมายทั้งหมดอยู่ใน [user-guide.md](user-guide.md#4-ถ้าจองไม่ได้--ความหมายของข้อความที่เจอ)

### "มีผู้อื่นแก้ไขการจองนี้ไปแล้ว"

สองคนแก้รายการเดียวกันพร้อมกัน ระบบกันไม่ให้เขียนทับ (optimistic concurrency)
**แก้:** โหลดหน้าใหม่แล้วแก้อีกครั้ง

### ห้องใหม่ที่เพิ่มแล้วไม่เห็นในปฏิทิน

1. ตรวจว่าติ๊ก **เปิดให้จองได้** ไว้
2. ตรวจว่าไม่ได้ถูกเก็บเข้าคลัง
3. โหลดหน้าปฏิทินใหม่

ถ้ายังไม่เห็น ให้ตรวจว่าเพิ่มลงฐานข้อมูลเดียวกับที่เว็บใช้อยู่จริง
(บางครั้งเพิ่มลง staging แต่ไปดูที่ production)

### การจองหายไปเอง

ตรวจ **บันทึกการใช้งาน** ค้นด้วย `booking.cancel` หรือ `booking.no_show`

| สิ่งที่พบ | หมายความว่า |
|---|---|
| `booking.no_show` | ห้องตั้งว่า "ต้องเช็กอิน" และไม่มีการเช็กอินทันเวลา ระบบจึงปล่อยห้องคืน |
| `booking.cancel` | มีคนยกเลิก — ดูชื่อผู้กระทำในบันทึก |
| `booking.rejected` | ผู้อนุมัติปฏิเสธ |
| `room.closure_create` | มีการปิดห้อง — การจองยังอยู่แต่ผู้จองได้รับแจ้งเตือน |

> ระบบ **ไม่ลบ** การจองทิ้ง เปลี่ยนสถานะเท่านั้น จึงตามรอยได้ทุกกรณี

## หมวด: การแจ้งเตือน

### อีเมลไม่ออกเลย

เปิดหน้า **ผู้ดูแลระบบ → สถานะระบบ** แล้วดูตามลำดับ

1. การ์ด "ผู้ให้บริการอีเมล" ขึ้น **โหมดทดสอบ (log)** หรือไม่
   → ตั้ง `EMAIL_PROVIDER=resend` ใส่ `EMAIL_API_KEY` แล้ว Redeploy
2. "งานค้างในคิว" มีจำนวนมากและค้างนานหรือไม่
   → Cron ไม่ทำงาน ตรวจ Vercel → Cron Jobs และค่า `CRON_SECRET`
3. ดู "ความผิดพลาดล่าสุด" จะเห็นสาเหตุจริงจากผู้ให้บริการ

| ข้อความที่เห็น | สาเหตุ | แก้อย่างไร |
|---|---|---|
| `HTTP 401` | API key ผิดหรือถูกเพิกถอน | สร้างคีย์ใหม่ → ใส่ → Redeploy → กด "ลองส่งใหม่" |
| `HTTP 403 ... domain not verified` | DNS ของอีเมลยังไม่ผ่าน | ทำตาม [dns-sheet.md](dns-sheet.md) ส่วนอีเมล |
| `HTTP 422 ... from address` | `EMAIL_FROM` ไม่ใช่โดเมนที่ verify | แก้ให้เป็นโดเมนที่ verify แล้ว |
| `HTTP 429` | ส่งเกินโควตา | ระบบ retry ให้เอง ถ้าเกิดต่อเนื่องให้ขยายแพ็กเกจ |

### อีเมลเข้า Junk / Spam

- ตรวจว่า SPF, DKIM, DMARC ผ่านครบ (`dig +short TXT ...`)
- ต้องมี **SPF record เดียวต่อหนึ่ง host** ถ้ามีสองใบให้รวมเป็นใบเดียว
- ส่งจาก subdomain แยก (เช่น `notify.example.com`) ไม่ใช้โดเมนหลัก
- ตรวจ "อีเมลที่ถูกระงับส่ง" ในหน้าสถานะระบบ — ถ้าเยอะแปลว่ามีอีเมลตีกลับมาก
  ซึ่งกระทบชื่อเสียงโดเมน

### ผู้ใช้บางคนได้อีเมล บางคนไม่ได้

- คนที่ไม่ได้อาจ **ปิดการแจ้งเตือนทางอีเมล** ไว้เอง (งานจะขึ้นสถานะ "ข้าม" ไม่ใช่ล้มเหลว)
- หรืออีเมลอยู่ในรายการระงับการส่งเพราะเคยตีกลับ

### LINE ไม่ออก

| อาการ | สาเหตุ | แก้อย่างไร |
|---|---|---|
| งานขึ้น "ข้าม" พร้อมข้อความเรื่องยังไม่เชื่อมบัญชี | ผู้ใช้ยังไม่เชื่อม LINE | แนะนำตาม [user-guide.md](user-guide.md#เชื่อมบัญชี-line) |
| `HTTP 401` | Channel access token หมดอายุ/ถูกเพิกถอน | ออก token ใหม่ → ใส่ → Redeploy → ลองส่งใหม่ |
| `HTTP 429` | เกินโควตาข้อความของแพ็กเกจ LINE | ลดจำนวนเวลาเตือนต่อคน หรือขยายแพ็กเกจ |
| ผู้ใช้เชื่อมบัญชีไม่สำเร็จ | webhook ล้ม | LINE Console → กด Verify และดู Vercel Logs ของ `/api/webhooks/line` |
| เคยได้แล้วหยุดไป | ผู้ใช้บล็อกบัญชีทางการ | ระบบตั้งสถานะเป็น blocked ให้เอง — ให้ผู้ใช้เลิกบล็อกแล้วเชื่อมใหม่ |

### รหัสเชื่อมบัญชี LINE ใช้ไม่ได้

- รหัสมีอายุ **15 นาที** และ **ใช้ได้ครั้งเดียว** — ขอรหัสใหม่
- ต้องพิมพ์รหัส 8 ตัวเท่านั้น ไม่มีข้อความอื่นปนในข้อความเดียวกัน
- ถ้า LINE user id นั้นเคยผูกกับบัญชีอื่น ระบบจะย้ายการผูกมาที่บัญชีใหม่ให้อัตโนมัติ

### เตือนก่อนประชุมไม่มา

1. ตรวจว่าผู้ใช้เลือกเวลาเตือนไว้ในหน้าโปรไฟล์
2. การเตือนถูกตั้งไว้ตอน **ยืนยันการจอง** — ถ้าแก้เวลาประชุม ระบบจะยกเลิกของเดิม
   และตั้งใหม่ให้อัตโนมัติ
3. ถ้าเวลาเตือนผ่านไปแล้วตอนจอง (เช่นจองก่อนประชุม 10 นาที แต่ตั้งเตือน 15 นาที)
   ระบบจะไม่ตั้งการเตือนนั้น — เป็นพฤติกรรมที่ถูกต้อง

## หมวด: ประสิทธิภาพและความเสถียร

### เว็บช้าหรือ timeout ตอนคนเข้าพร้อมกัน

**สาเหตุอันดับหนึ่งของโปรเจกต์นี้:** `DATABASE_URL` ใช้พอร์ต **5432** แทน 6543

```
# ผิด — Session mode ทำให้ connection เต็มบน serverless
postgresql://postgres.xxx:pw@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres

# ถูก — Transaction pooler
postgresql://postgres.xxx:pw@aws-0-ap-southeast-1.pooler.supabase.com:6543/postgres
```

แก้แล้ว **Redeploy** ทันที และตรวจว่า `DATABASE_POOL_MAX` ไม่เกิน 5

ตรวจจำนวน connection ได้ที่ Supabase → Reports → Database

### `/api/health` ตอบ 503 `database: down`

1. Supabase Dashboard → สถานะโปรเจกต์เป็นสีเขียวไหม
2. โปรเจกต์ Free tier ถูกพักเพราะไม่มีใครใช้เกิน 7 วันหรือไม่ → กด Restore project
3. <https://status.supabase.com> มีเหตุขัดข้องหรือไม่
4. รหัสผ่านฐานข้อมูลถูกเปลี่ยนหรือไม่

### ปฏิทินโหลดช้าเมื่อเลือก "ทุกห้อง"

เป็นพฤติกรรมปกติเมื่อมีห้องจำนวนมาก — เลือกห้องเดียวจะเร็วกว่า
ถ้าช้ามากผิดปกติ ให้ตรวจว่า index ยังอยู่

```sql
select indexname from pg_indexes where tablename = 'bookings';
-- ต้องเห็น bookings_room_time_idx และ bookings_period_gist_idx
```

## หมวด: งานตามเวลา

### Cron ไม่ทำงาน

| ตรวจ | คาดหวัง |
|---|---|
| Vercel → Cron Jobs | เห็นสองรายการจาก `vercel.json` |
| เรียกโดยไม่ใส่ header | ได้ **403** |
| เรียกด้วย `CRON_SECRET` ถูก | ได้ **200** |

```bash
curl -H "authorization: Bearer $CRON_SECRET" https://meeting.example.com/api/cron/dispatch
```

ถ้าเรียกโดยไม่ใส่ header แล้วได้ **200** แปลว่ายังไม่ได้ตั้ง `CRON_SECRET`
→ ตั้งทันที เพราะเป็นช่องให้คนนอกสั่งงานระบบได้

### งานค้างในคิวเยอะขึ้นเรื่อย ๆ

1. เรียก Cron ด้วยมือหนึ่งรอบ แล้วดูว่าตัวเลข `sent` เพิ่มขึ้นไหม

### สงสัยว่ามีคนพยายามเดารหัสผ่าน

```sql
select email, count(*), max(attempted_at) from login_attempts
where not succeeded and attempted_at > now() - interval '24 hours'
group by email order by count(*) desc limit 20;
```

ระบบจำกัดอัตราให้อยู่แล้ว (8 ครั้ง/15 นาที ต่ออีเมล และ 24 ครั้ง/15 นาที ต่อ IP)
และบันทึก `auth.login_rate_limited` ลง audit log
ถ้าเจอบัญชีที่ถูกโจมตีหนัก ให้ตั้งสถานะเป็น **ถูกระงับ** ชั่วคราวและแจ้งเจ้าของบัญชี

### ผู้ใช้เห็นข้อมูลที่ไม่ควรเห็น

**ถือเป็นเรื่องร้ายแรง** ให้ทำตามลำดับ

1. บันทึกหลักฐาน (แคปหน้าจอ เวลา บัญชีที่ใช้)
2. ตรวจว่า RLS ยังเปิดและ FORCE อยู่

```sql
select relname, relrowsecurity, relforcerowsecurity from pg_class
where relname in ('bookings','profiles','audit_logs','user_roles');
-- ทุกแถวต้องเป็น t, t
```

3. ตรวจว่าผู้ใช้นั้นได้รับสิทธิ์เกินจริงหรือไม่

```sql
select p.email, ur.role_code, ur.scope_type, ur.scope_id
from profiles p join user_roles ur on ur.profile_id = p.id
where lower(p.email) = lower('user@example.com');
```

4. ถ้าสิทธิ์ถูกต้องแต่ยังเห็นข้อมูล ให้แจ้งทีมพัฒนาพร้อม `correlationId`
   และพิจารณาระงับบัญชีที่เกี่ยวข้องชั่วคราว

**ก่อนแจ้งทีมพัฒนา ให้เตรียมข้อมูลเหล่านี้** จะช่วยให้แก้ได้เร็วขึ้นมาก

- อาการที่เห็น และข้อความบนหน้าจอแบบคำต่อคำ
- เวลาที่เกิด (ระบุโซนเวลา)
- บัญชีและสิทธิ์ของผู้ใช้ที่เจอปัญหา
- `correlationId` จาก response header `x-correlation-id`
- เกิดกับทุกคนหรือเฉพาะบางคน / ทุกเบราว์เซอร์หรือบางเบราว์เซอร์
- ผลของ `curl -s https://meeting.example.com/api/health`
